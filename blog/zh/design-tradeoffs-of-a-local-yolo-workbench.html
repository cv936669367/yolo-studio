把 Roboflow 那套流程搬回本地之后，我们做了哪几个取舍

2026-10-26约 5 分钟

一篇偏工程决策的说明：YOLO Studio 为什么这样设计，以及它现在明确做不到什么。

项目地址：https://github.com/cv936669367/yolo-studio （MIT，另有 Gitee 镜像 https://gitee.com/btdba/yolo-studio）

一、起因：图片不能出内网

很多团队的视觉需求长这样：识别自己产线上的某种零件、某批包装、某个工位上的异常。图片往往带着客户信息、工艺细节，或者合同里就写着"不得上传第三方平台"。

Roboflow 把这条流程设计得很好：建项目、传图、辅助标注、划分数据、训练、评估，一路点下来就能得到一个能用的模型。问题只有一个——它默认图片要离开你的机器。

换成完全本地的方案，通常是这样拼起来的：CVAT 标图，Jupyter Notebook 训练，再用一个 Excel 记住哪个 best.pt 是哪次跑出来的、对应哪版数据。能跑通，但每换一批图片就要重新拼一次管线；换个人接手，先要花半天搞清楚目录结构。

YOLO Studio 想做的事很朴素：把这条流水线收回一台机器，浏览器打开就能用。 技术栈也不复杂——后端 FastAPI + SQLAlchemy(async) + SQLite，前端 Vue 3 + Element Plus + Vite，训练真实调用 Ultralytics，SAM 走 Ultralytics 的封装，MIT 协议。

标注工作台：SAM 生成的是可编辑的多边形轮廓（示例 120 个顶点），不是一张扁平掩码。

下面是我们在这件事上做的几个取舍，按重要性排。

二、取舍一：SQLite 单机，而不是做一个服务

最容易被质疑的决定：为什么不做成 Web 服务、多人协作、对象存储？

因为目标场景就是"一台机器、一个人、一个项目"。选定这个前提之后，很多复杂度是自找的：

  • 数据用 SQLite，不用 Postgres，不需要部署数据库；
  • 图片、权重、训练产物直接落在 backend/data/，备份就是拷目录；
  • 没有任务队列，训练用后台线程，进度写内存再由前端轮询；
  • 删除工程时，数据库记录、上传图片、训练产物一起清掉，不留孤儿文件。

好处是数据完全可见：每一张图、每一条标注、每一次训练记录，都能用任意 SQLite 工具打开看。坏处也很直接——没有并发、没有多用户、没有权限体系。它是个工作台，不是平台。

三、取舍二：让 SAM 只负责几何，不负责语义

这是整个项目里最关键的一条设计。

SAM（Segment Anything）很强，但它强在"你指的这一块，边界在哪"，而不是"这是什么"。所以接口从头到尾都按"几何工具"来设计：

人给位置提示 → SAM 返回掩码 → 转成归一化多边形 → 人确认类别和边界。

框选模式用一个矩形告诉 SAM 大概范围；点选模式用左键加正点、右键加负点，逐步把背景排掉。两种模式最终产出的都是可编辑的多边形点集，不是一张栅格掩码——因为标注的价值在于后续能改、能进训练，而不是好看。

这里有个实现细节值得单独说，因为它踩过一次：SAM 的点提示，points 和 labels 的形状是 (batch, n_points, 2) 和 (batch, n_points)。如果按直觉写成 (N, 2)，Ultralytics 会理解成"N 张图，每张一个点"，结果只有第一个点生效，而且不报错——你只会看到轮廓莫名其妙不对。

正确的写法是加一层 batch 维度：

sam_points = [[[int(p["x"] * img_w), int(p["y"] * img_h)] for p in pts]]
sam_labels = [[1 if p.get("positive", True) else 0 for p in pts]]
model.predict(str(img_path), points=sam_points, labels=sam_labels)

拿到掩码之后还有两步转换：先归一化（存的是 0~1 的相对坐标，窗口缩放、换分辨率都不会错位），再抽稀。抽稀用的是距离阈值 0.006（约千分之六边长）+ 点数上限 120，超过上限就等距取样。之所以要限制，是因为编辑器每个鼠标移动都要重绘顶点，而一个四千点的轮廓，人也没法改。

这个抽稀方案是妥协，不是最优。 它按距离筛点、按顺序取样，不是 Ramer–Douglas–Peucker，所以尖锐的转角可能被一起丢掉，而直边反而保留了很多点。RDP 在同样点数下形状保真更好，这是我们后面要换的。

四、取舍三：上一轮的模型，是下一轮的标注工具

单点功能都好抄，难的是让上一环节的产出成为下一环节的输入。这个项目里最值钱的一条链路是：

手动标一批 → 训练第一版 → 用这版 best.pt 预标注下一批 → 人工复核 → 再训练。

预标注有两个入口：

  • 基线模型：下载任务匹配的 YOLOv8 预训练权重，按工程类别做名称匹配，生成检测框或分割轮廓；
  • 工程模型：用本工程已经训练完成的 best.pt，对后续图片批量推理，检测工程出框、分割工程出轮廓。

第一条有个必须说清楚的坑：基线模型只认识它训练过的类别，匹配方式是类名字面比较。 你的工程里如果叫 drinks，COCO 的 bottle 不会自动对应过去。想识别自己的业务类别，绕不开"先标一批、再训练"这一步。

而这也正是第二条的价值：第一轮之后，模型认识的是你的类别，预标注才真的开始省时间。人的工作从"画轮廓"逐渐变成"改错、补漏"——这是唯一能在真实脏数据上站得住的提速。

批量预标注支持选范围、调置信度、中途取消，已完成的标注会保留。分割工程要额外注意：轮廓不可用时会回退成四角多边形，这些回退结果必须人工看一眼，否则会悄悄污染下一轮训练集。

五、取舍四：中文优先，和"国内能下载"

界面是中文的，Element Plus 也锁定 zh-cn，没有 i18n 层——字符串直接写在 Vue 组件里。对海外用户这是明确的门槛，我们认。

另一件更实际的事是权重下载。github.com 的 release 资源在国内经常下不动，而 SAM-B 有 375MB，下不下来直接决定智能标注能不能用。所以下载逻辑是：先试几个公共 GitHub 加速地址（gh-proxy.com、ghfast.top、ghproxy.net），失败回退官方源，全程有进度条。

需要说明的是：这不是"我们自建了国内镜像"，只是把公共加速服务做成默认顺序，并保留官方源兜底。

六、取舍五：训练设备只做 MPS / CPU

代码里就一行：

device = "mps" if torch.backends.mps.is_available() else "cpu"

没有 CUDA 分支。原因很现实：开发用的是 Mac。代价是 NVIDIA 机器上虽然能跑，但走的是 CPU——小数据集可接受，大数据集会很难受。这一条我们在 README 里没有美化，这里也一样。

七、它现在明确做不到的事

写清楚边界比列功能更有用：

  1. 界面只有中文，没有 i18n 层；
  2. 没有 CUDA 分支，NVIDIA 机器走 CPU；
  3. 依赖锁定 ultralytics==8.3.0，模型列表里有更新的系列，但权重能否加载取决于实际安装的 Ultralytics 版本，建议从 YOLOv8 开始；
  4. 单用户、无鉴权，不要暴露到不受控的网络；
  5. 验证页的指标卡读取的是框指标，分割工程还要另外看掩码指标和轮廓质量；
  6. 验证集为空时会借一张训练图（Ultralytics 要求 val 非空），所以要自己准备独立、标注完整的验证集，别把"能开始训练"当成"评估条件可靠"；
  7. 预标注按类名精确匹配，自定义类别必须先训练；
  8. 轮廓抽稀不是 RDP，细长结构、透明反光物体的边界仍建议手工修。

八、如果你要试

git clone https://github.com/cv936669367/yolo-studio
cd yolo-studio/backend
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt
uvicorn main:app --reload --port 8000

# 另开一个终端
cd ../frontend && npm install && npm run dev

浏览器打开 http://localhost:3000，第一次会创建 backend/data/。想用 SAM 智能标注，先在标注页下载 sam_b.pt（约 375MB）。

如果你在真实项目里试了，欢迎把"卡在哪一步"发到 issue——尤其是操作系统、Python 版本和报错。上面那份"做不到"的清单，就是靠这种方式一点点变短的。
