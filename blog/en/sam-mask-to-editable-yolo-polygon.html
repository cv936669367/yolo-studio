SAM returns a mask. YOLO wants a polygon. Here's the pixel math in between.

2026-10-265 min readcomputervisionpythonmachinelearningopensource

Segment Anything is very good at answering one question: given this prompt, which pixels belong to the object? YOLO is very good at answering a different one: given this image, where are all the objects of these classes? Putting them in the same tool means crossing a format gap that looks trivial and isn't.

This is a walkthrough of that gap as it's implemented in YOLO Studio, an MIT-licensed local labeling + training workbench. The whole conversion is about 120 lines of Python in backend/api/ai_annotate.py, and most of the interesting decisions are in the details.

The three coordinate systems

A single click passes through three representations before it becomes a label:

  1. Browser pixels. The canvas is scaled, panned and sometimes tiled, so the raw mouse position means nothing on its own.
  2. Normalized image coordinates, 0..1 relative to the original image. Everything stored in the annotation table uses this, which is why annotations survive window resizing, zooming and different viewport sizes.
  3. Original-image pixels. SAM wants integers in the source image's coordinate space, and Ultralytics' predict call takes them that way.

So the front end normalizes before sending, and the backend multiplies back up:

box_xyxy = [
    int(x * img_w), int(y * img_h),
    int((x + w) * img_w), int((y + h) * img_h),
]

Storing normalized points rather than pixels has a second benefit: the training exporter doesn't need to know the original resolution. YOLO segmentation labels are normalized anyway.

The shape bug that eats your clicks

SAM's point prompts take two tensors: points and labels. The shape is (batch, n_points, 2) and (batch, n_points).

The natural-looking version is wrong:

# Wrong: interpreted as N images, each with one point
points = [[x1, y1], [x2, y2]]

Ultralytics reads a (N, 2) array as N separate images with one prompt each, so only the first click actually lands on your image. The working shape adds a batch dimension:

sam_points = [[[int(p["x"] * img_w), int(p["y"] * img_h)] for p in pts]]
sam_labels = [[1 if p.get("positive", True) else 0 for p in pts]]

results = model.predict(
    str(img_path),
    points=sam_points,   # (1, N, 2)
    labels=sam_labels,   # (1, N): 1 = include, 0 = exclude
    verbose=False,
)

We left a comment above that line because the failure mode is silent: no exception, no warning, just a mask that ignores everything after the first point.

Picking one mask out of several

A box prompt usually comes back with more than one candidate mask. We score them by polygon area and keep the largest:

best_idx, best_area = 0, 0
for i, xy in enumerate(masks.xy):
    if len(xy) >= 3:
        area = abs(sum(
            xy[j][0] * xy[(j + 1) % len(xy)][1] - xy[(j + 1) % len(xy)][0] * xy[j][1]
            for j in range(len(xy))
        ) / 2)
        if area > best_area:
            best_area, best_idx = area, i

The shoelace formula runs on the returned contour in pixel space, so no extra mask decoding is needed. Largest-area is a heuristic with a clear failure case: if your box covers two objects, you get the bigger one and silently lose the other. A multi-mask picker in the UI (small/medium/large candidates, like the SAM demo) is the right fix; we haven't built it.

Mask → normalized polygon → simplify

masks.xy gives one contour per instance as a list of pixel points. Those get normalized, then simplified, because raw SAM contours can be hundreds or thousands of vertices — unusable in a hand-editable polygon and wasteful in a label file:

points_norm = [{"x": round(p[0] / img_w, 6), "y": round(p[1] / img_h, 6)} for p in poly_px]

def _simplify_polygon(points, min_dist=0.006, max_points=120):
    simplified = [points[0]]
    for p in points[1:]:
        last = simplified[-1]
        if (p[0] - last[0])**2 + (p[1] - last[1])**2 >= min_dist**2:
            simplified.append(p)
    ...
    if len(simplified) > max_points:
        step = len(simplified) / max_points
        simplified = [simplified[int(i * step)] for i in range(max_points)]
    return simplified

Two parameters, both normalized so they behave the same on a 640 px and a 6000 px image:

  • min_dist = 0.006 drops points closer than about 6 px per 1000 px of image width. Small enough to keep the shape of a bottle shoulder, big enough to collapse a straight edge into a couple of vertices.
  • max_points = 120 is a hard cap, enforced by uniform subsampling. The cap exists because the annotation editor redraws handles on every mouse move, and because a 4000-point label is not something a human can meaningfully correct.

The honest trade-off: this is a distance filter plus a stride, not Ramer–Douglas–Peucker. It preserves vertices uniformly rather than by geometric importance, so a sharp corner between two close points can be dropped while a straight run keeps more points than it needs. RDP with a small epsilon would give better shape fidelity at the same point count; it's on the list.

Preview mode: the difference between a guess and a tool

A point-prompt flow is iterative — click, look, click again, remove a point, look again. Writing every intermediate result to the database would be silly, and would also make "undo" ambiguous.

So the endpoint has a preview flag:

if data.preview:
    return {"success": True, "points": points, "points_count": len(points)}

The front end accumulates positive and negative points, re-requests a preview on each change, draws the returned polygon as an overlay, and only on confirm does it create the annotation. Same code path, no database churn, and the user's mental model matches the implementation: you are editing a shape, not saving a series of mistakes.

From annotation to a training label

Polygon annotations are stored as a normalized point list. When a training run starts, the exporter writes YOLO segmentation format — one line per instance:

0 0.5123 0.2210 0.5231 0.2234 0.5290 0.2391 ...

Rectangles are a special case: in a polygon project, a rectangle annotation becomes a four-corner polygon, because a segmentation model can't consume box labels. Detection projects go the other way — polygon annotations are reduced to their bounding box. That asymmetry is the kind of thing that's obvious in hindsight and confusing when it bites you at export time.

Where it breaks

  • Thin structures. Wires, cables, thin seams. The distance filter plus a 120-point cap will cut a cable into a few straight segments. Manual polygon editing is genuinely better here.
  • Transparent and reflective objects. The bottle in our screenshots is the hard case, not the easy one: the mask tends to leak into what's visible through the object. Negative points help; nothing fully solves it.
  • Objects touching the frame edge. SAM will happily segment past the border; the normalized points are still clipped to 0..1 at write time, so the polygon follows the edge.
  • Very small objects. If the mask yields fewer than three points after simplification, the call returns "segmentation too small" rather than writing a degenerate label. At that size, a box is the more honest annotation.
  • Model download. SAM-B is ~375 MB. The app fetches it from a mirror with an official-source fallback, and refuses to pretend the feature works before the download finishes.

What this buys you

The point of all this plumbing is one behaviour: when SAM gets the outline right — which for clean, well-framed industrial objects is most of the time — labeling a bottle becomes one drag plus one click, and the result is an editable polygon rather than a raster mask. The human stays in charge of the class, the boundary conventions, and the cases the model gets wrong, which is exactly where human time should go.
